# SockCheck.ai

SockCheck.ai is a visual clothing search application developed as a capstone project. A user uploads a photograph of a garment, and the system returns the most visually similar items from a catalog of clothing images, ranked by similarity. The goal is to give users outfit inspiration drawn from a large library of clothing combinations.

## How It Works

1. **Detection.** GroundingDINO locates the garment in the uploaded image using the text prompt `shirt . jacket . pants`.
2. **Segmentation.** A segmentation mask isolates the garment from the background. This is performed either by Meta's Segment Anything Model (SAM) or by a smaller "student" model trained on SAM's masks (see [Segmentation Models](#segmentation-models)).
3. **Cropping.** The image is cropped to the garment's bounding box, and pixels outside the mask are filled with a neutral background.
4. **Embedding.** The crop is encoded into a 512-dimensional vector using FashionCLIP (`patrickjohncyh/fashion-clip`).
5. **Retrieval.** The vector is compared against the catalog embeddings stored in PostgreSQL with the pgvector extension, using cosine similarity. Results are restricted to the detected garment category.

## Architecture

| Component | Technology | Location |
| --- | --- | --- |
| Web client | Next.js 16, React 19, Tailwind CSS 4 | `client/` |
| API | FastAPI, served with Uvicorn on port 8000 | `backend/` |
| ML pipeline | PyTorch, GroundingDINO, SAM, Hugging Face Transformers | `Data_Manipulation_Pipeline/` |
| Database | PostgreSQL with pgvector and pgcrypto | `Data_Manipulation_Pipeline/schema.sql` |
| Image storage | Cloudflare R2 | catalog images, and user uploads on the history branch |

The Next.js client proxies all `/api/*` requests to the FastAPI server (configured in `client/next.config.mjs`), so session cookies remain same-origin.

## Features

- **Similarity search.** Upload an image and receive the closest catalog matches with similarity scores.
- **Drag-and-drop upload.** The upload page accepts dropped images or a selection through the system file browser, with a brief animated frame as feedback on drop.
- **User accounts.** Registration, login, and logout use JWT session cookies (HttpOnly, 7-day lifetime). Passwords are hashed in PostgreSQL with pgcrypto (bcrypt).
- **Anonymous usage limit.** Visitors without an account may make 2 requests, tracked through an HMAC-signed cookie. After that, `/predict` returns HTTP 429 and the interface prompts the user to register.
- **Wardrobe history.** Logged-in users can browse previous uploads together with the top three stored matches, and delete entries. The page reads stored results from `inference_results` and does not rerun inference. User photos are held in a separate, non-public R2 bucket and are returned only to their owner through the API.

## Segmentation Models

SAM is accurate but slow, partly because it is designed to produce multiple candidate masks per image. Because this application needs only one mask per image, a smaller student model was trained on masks generated by SAM.

| Approach | Mean IoU | Notes |
| --- | --- | --- |
| Bounding-box fill (baseline) | 0.648 | Fills the detected box |
| Student model | 0.977 | About 9.2 ms per mask, excluding box generation and embedding |

These figures were measured on images of clothing worn by people. They do not describe accuracy on garments laid flat. At startup, the API uses the student model if `STUDENT_CKPT` points to a valid checkpoint, and falls back to SAM otherwise.

## Database Schema

- `images` and `embeddings`: one row per catalog garment crop, with its category and 512-dimension vectors. Multiple embeddings per image are permitted so images can be re-embedded with newer models; searches use the most recent one.
- `users`: account records with hashed passwords.
- `past_inference`, `user_images`, `inference_results`: one inference per uploaded photo, the stored upload location, and the ranked matches with similarity scores.

## Setup

There is currently no pinned dependency file for the backend. The environment needs, at minimum, FastAPI, Uvicorn, psycopg, pgvector, python-dotenv, python-jose, Pillow, PyTorch, Transformers, boto3, GroundingDINO, and Segment Anything. GroundingDINO and SAM checkpoints must be downloaded separately.

### Database

Create a PostgreSQL database with the pgvector and pgcrypto extensions available, then apply `Data_Manipulation_Pipeline/schema.sql`. Catalog images are loaded with `annotate.py`, `embed_transformers.py`, and `vectors_to_pg.py`, and can be moved to R2 with `migrate_to_r2.py`.

### Backend configuration

Create `backend/.env` with the following values:

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | PostgreSQL connection string |
| `AUTH_SECRET_KEY` | Secret used to sign session tokens and the anonymous cookie. Must be set outside development. |
| `GDINO_CONFIG`, `GDINO_CKPT` | GroundingDINO config and checkpoint paths |
| `SAM_CKPT`, `SAM_MODEL` | SAM checkpoint path and model type (for example `vit_b`) |
| `DEVICE` | Torch device, for example `cpu` |
| `STUDENT_CKPT` | Optional. Student model checkpoint; SAM is used if unset or missing. |
| `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` | Cloudflare R2 credentials |
| `R2_USER_BUCKET` | Name of the private bucket for user uploads (history branch). Must not be a public bucket. |

### Running

Start the API from the repository root, since the backend imports `backend` and `Data_Manipulation_Pipeline` as packages:

```bash
uvicorn backend.main:app --port 8000
```

Start the client in a second terminal:

```bash
cd client
npm install
npm run dev
```

The application is then available at `http://localhost:3000`.

## Project Status

Development is organized by branch, and these lines of work have not yet been merged into one another:

- **`front-end`** (current): the redesigned interface, including the drag-and-drop upload page and its drop animation.
- **`model-updates`**: the student segmentation model and the updated pipeline entry point that uses it.
- **`feature/past-inference`**: the wardrobe history page, history and delete endpoints, and private R2 storage for user uploads. It also contains the `model-updates` changes.

The student model and wardrobe history are therefore absent from `front-end` until those branches are merged.

Known limitations:

- Only one garment per image is handled; the first detected instance is used.
- Inference currently runs on the CPU in the reference setup.
- Segmentation accuracy figures apply to worn clothing only.
- The history feature has not yet been tested end to end against R2.
- Wardrobe entries are created only for uploads made after the history feature is deployed.
